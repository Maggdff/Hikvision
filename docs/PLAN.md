# VoiceUp — خطة التنفيذ والمعمارية وتقدير التكلفة

الإصدار 0.1 — 21 نوفمبر 2026 — مبنية على مواصفتي المشروع والنظام المالي.

---

## 0. ملخص تنفيذي وقرارات تحتاج تأكيدك

**ما سيُبنى:** تطبيق Android لغرف صوتية عربية (Kotlin + Compose + Material 3)، وخادم Backend، وقاعدة بيانات مالية محاسبية، ولوحتا ويب (إدارة + وكالات).

**ثلاثة أمور جوهرية كشفتها دراسة المواصفتين:**

1. **تعارض بين المواصفتين.** الأولى تقول "لا نظام سحب نقدي". الثانية تُنشئ صندوق مكافآت ومستحقات وتسوية للمضيفات والوكالات. اعتمدتُ المواصفة الثانية (الأحدث) بشرط: لا تحويل أموال بين المستخدمين أبداً، والسحب مغلق بـ Feature Flag ولا يُفتح قبل اجتياز البنود القانونية (القسم 9).
2. **Firestore وحده لا يصلح للدفتر المحاسبي.** المواصفة تشترط NUMERIC، قيوداً غير قابلة للتعديل، معاملات ذرية متعددة الجداول، وMigrations. لذلك: **PostgreSQL للمال والوكالات**، و**Firebase للمصادقة والتخزين والإشعارات وبيانات الواجهة الخفيفة**.
3. **مشتريات النقاط يجب أن تمر عبر Google Play Billing** (سلع رقمية). هذا يعني رسوم متجر تُخصم من الإيراد، وهو ما يتوافق مع تعريف Net Eligible Gift Revenue في مواصفتك.

## 1. المعمارية

```
┌────────────── Android (Kotlin / Compose / M3) ──────────────┐
│ presentation (Compose + ViewModel)  ←  MVVM                  │
│ domain (UseCases, Models)           ←  Clean Architecture    │
│ data (Repositories, Retrofit, Room cache, LiveKit SDK)       │
└──────────────┬───────────────────────────┬──────────────────┘
               │ HTTPS + Firebase ID Token │ WebRTC (SFU)
       ┌───────▼────────┐          ┌───────▼────────┐
       │  VoiceUp API   │          │ LiveKit Cloud  │
       │ (Cloud Run)    │◄─webhook─┤  (أو Agora)    │
       └───┬────────┬───┘          └────────────────┘
           │        │
  ┌────────▼──┐  ┌──▼────────────────────────────┐
  │ PostgreSQL│  │ Firebase: Auth, Storage, FCM, │
  │ (Cloud SQL)│ │ Firestore (دردشة الغرف/الحضور)│
  └───────────┘  └───────────────────────────────┘
       ▲
┌──────┴─────────────────────────┐
│ Admin Web + Agency Web (Next.js)│
└─────────────────────────────────┘
```

### المبادئ
- **لا أسرار في التطبيق.** رموز LiveKit تُصدر من الخادم فقط (JWT قصير العمر، صلاحيات حسب الدور: مستمع / متحدث / مشرف). مفاتيح API في Secret Manager.
- **الخادم هو مصدر الحقيقة** للأدوار والمقاعد والمال. التطبيق لا يقرر شيئاً حساساً.
- **الصوت:** LiveKit كخيار أول (مفتوح المصدر، يمكن استضافته ذاتياً لاحقاً). Agora بديل جاهز عبر واجهة `VoiceEngine` في طبقة domain.
- **دردشة الغرفة والحضور:** Firestore (استماع لحظي رخيص التطوير)، مع قواعد أمان صارمة وحدود معدل عبر الخادم.
- **المال:** PostgreSQL فقط. لا يُكتب إليه إلا من الخادم.

### التقنيات المقترحة للخادم واللوحات
| الطبقة | الاختيار | السبب |
|---|---|---|
| API | Node.js + TypeScript (Fastify) | سرعة التطوير، نظام Firebase Admin ناضج |
| DB | PostgreSQL + Migrations (Drizzle/Knex) | NUMERIC، معاملات، قيود |
| لوحات الويب | Next.js + Tailwind (RTL) | لوحة الإدارة ولوحة الوكالات |
| CI | GitHub Actions | APK + اختبارات الخادم |
| الاستضافة | Cloud Run + Cloud SQL | توسع تلقائي، تكلفة تبدأ منخفضة |

## 2. نموذج البيانات (مختصر)

**الهوية والاجتماع (PostgreSQL + Firestore):** users, profiles, follows, friendships, blocks, reports, moderation_actions, rooms, room_members, room_roles, seat_requests.

**المالية (PostgreSQL فقط):**
- `ledger_accounts`, `ledger_entries`, `ledger_transactions` — قيد مزدوج، **Append-only** (Trigger يمنع UPDATE/DELETE).
- `point_purchases` (مرتبطة بإيصال Play Billing + رسوم المتجر + ضريبة).
- `gift_transactions` (Idempotency-Key فريد، حالة: confirmed / refunded / cancelled).
- `agencies`, `agency_memberships` (سجل تاريخي، وكالة نشطة واحدة لكل مضيفة عبر قيد فريد جزئي)، `hosts`.
- `rule_sets` + `rule_versions` — **كل النسب والتارجت والأوزان مخزنة بإصدارات** ولا قيم ثابتة في الكود. تُثبَّت نسخة القواعد لكل فترة شهرية عند بدايتها فلا أثر رجعي.
- `monthly_periods`, `host_period_stats`, `agency_period_stats`, `reward_pool_allocations`, `payables`, `settlements`.
- `fraud_signals`, `fraud_reviews`, `appeals` — الإشارات الآلية لا تصادر المستحقات؛ تُجمَّد فقط بانتظار مراجعة بشرية.

**قواعد صارمة:** Decimal فقط، العملة والتقريب (Banker's أو Half-up) معرَّفان في القواعد، وكل حساب قابل لإعادة التشغيل (Deterministic) من القيود.

## 3. المنطق المالي (ملخص تطبيق المواصفة)

```
Net Eligible Gift Revenue (NEGR) = إيراد الهدايا المؤكدة
    − استردادات − إلغاءات − ضرائب مستبعدة − رسوم المتجر/الدفع

عمولة الوكالة  = NEGR(هدايا مضيفات الوكالة) × نسبة الشريحة
شرائح افتراضية: <50% → 5% | 50–74% → 8% | 75–99% → 10% | ≥100% → 15%
صندوق المضيفات = NEGR × 25% (قابل للتعديل)، يوزَّع بأوزان معلنة، ومجموعه ≤ الصندوق
تارجت المضيفة: Bronze 20k | Silver 50k | Gold 100k | Diamond 200k نقطة (ليست أموالاً)
```

- النقاط/الرصيد الافتراضي، قيمة الهدية، الإيراد المحاسبي، المستحق، الربح: **خمسة مفاهيم منفصلة** بحسابات منفصلة.
- منع الخصم المزدوج: Idempotency-Key + معاملة ذرية + قفل صف على المحفظة.
- لا تحويل نقاط بين المضيفات (قيد في المخطط + اختبار).

## 5. تقدير التكلفة (قبل اعتماد أي خدمة)

> الأرقام مأخوذة من صفحات الأسعار الرسمية وقت البحث وهي **تقديرية**؛ راجعها قبل الاعتماد. لم أحتسب الضرائب أو رسوم Google Play (15–30%) هنا لأنها تُخصم من الإيراد لا من المصاريف.

### 5.1 الصوت الفوري (أكبر بند)
| المزود | الأسعار الحالية |
|---|---|
| **LiveKit Cloud** | Build مجاني (5,000 دقيقة اتصال/شهر، للتجربة فقط). Ship: $50/شهر ويشمل 150 ألف دقيقة ثم $0.0005/دقيقة. Scale: $500/شهر ويشمل 1.5 مليون دقيقة ثم $0.0004/دقيقة. مع احتساب النطاق الترددي المنقول بالـ GB حسب الخطة. |
| **Agora** | 10,000 دقيقة مجانية شهرياً، ثم $0.99 لكل 1000 دقيقة مشارك (الصوت)، وخصومات حجم تبدأ من 100 ألف دقيقة. |

**سيناريوهات (دقائق مشاركين شهرياً، صوت فقط، دون النطاق الترددي):**

| السيناريو | دقائق/شهر | LiveKit | Agora |
|---|---|---|---|
| تجريبي: 200 مستخدم نشط يومياً × 30 د | 180 ألف | Ship ≈ **$65** | ≈ **$170** |
| إطلاق: 1,000 × 45 د/يوم | 1.35 مليون | Ship ≈ **$650** | ≈ **$1,300** |
| نمو: 10,000 × 60 د/يوم | 18 مليون | Scale ≈ **$7,100** | ≈ **$16,000+** بعد الخصومات |

**التوصية:** ابدأ بـ LiveKit (Ship)، ويمكن لاحقاً استضافته ذاتياً على خوادم خاصة عند الوصول لأحجام كبيرة لخفض التكلفة مقابل عبء تشغيلي. ملاحظة: الدقائق تحسب لكل مستمع متصل، لا للمتحدثين فقط، لذا إغلاق الاتصال عند خروج التطبيق للخلفية يوفر مالاً حقيقياً.

### 5.2 Firebase (خطة Blaze مطلوبة لـ Cloud Functions وأكثر)
- Auth: مجاني للبريد/الاجتماعي. **الهاتف (SMS) يُحاسَب بكل رسالة** — يفضَّل Google/البريد أولاً.
- Firestore: مجاني حتى 50 ألف قراءة و20 ألف كتابة يومياً، ثم حسب الاستهلاك. الدردشة الحية هي أكثر ما يستهلك؛ تصميم الاستماع (Pagination + Limit) أساسي.
- Storage: 5 GB مجاناً ثم $0.10/GB تقريباً.
- التقدير: **$0–$30/شهر** في التجربة، **$100–$600/شهر** عند آلاف المستخدمين النشطين حسب كثافة الدردشة.

### 5.3 الخادم وقاعدة البيانات والويب (تقدير تقريبي)

### 5.4 تكاليف لمرة واحدة
- حساب Google Play Developer: **$25** مرة واحدة.
- مراجعة قانونية ومحاسبية للنموذج المالي والعقود: **غير مشمولة**، وهي ضرورية قبل تفعيل أي مستحقات (انظر القسم 9).

### 5.5 المجموع التقريبي الشهري
- **تجريبي:** ≈ **$100–$200**.
- **إطلاق (1,000 نشط يومياً):** ≈ **$900–$1,600**، والصوت أكثر من نصفه.

## 6. التصميم (UI/UX)

- نظام تصميم Material 3 مخصص: خلفية داكنة، تدرجات (بنفسجي/أزرق/وردي كهربائي)، زوايا مستديرة كبيرة، إضاءة ناعمة على المقاعد المتحدثة.
- RTL أصلي (`start/end`، لا `left/right`)، خطوط عربية (مثل Cairo/Tajawal)، واختبار الأرقام والتواريخ.
- شاشات رئيسية: الرئيسية، غرفة صوتية (شبكة المقاعد + دردشة + أشرطة هدايا)، الملف الشخصي، الرسائل، الإشعارات، الإعدادات، المحفظة، مركز البلاغات، لوحة المضيفة (التارجت الفردي والجماعي منفصلان).
- حركات: Shared Element للغرفة، نبضة صوتية للمتحدث، هدايا بـ Lottie/Compose Canvas (خفيفة).
- أصول الهدايا: تصاميم أصلية فقط، لا استخدام لشخصيات أو علامات تجارية محمية.

## 7. الأداء والموثوقية

- إعادة اتصال تلقائية بالغرفة (Backoff أسي) وإعادة جلب رمز جديد.
- وضع توفير البيانات: ترميز Opus بمعدل منخفض للمستمعين، ولا فيديو.
- ذاكرة تخزين محلية (Room) للصفحة الرئيسية والملف الشخصي.
- تحميل الصور تدريجياً (Coil) مع أحجام متعددة في Storage.
- حدود المعدل ومنع الإغراق على الدردشة والهدايا.

## 8. الأمان والإشراف

- **التحقق العمري:** تاريخ الميلاد عند التسجيل. المزايا المالية (مضيفة/وكالة) لبالغين موثَّقين فقط. القاصرون لا يرسلون هدايا ولا ينضمون لغرف مرتبطة بدخل المضيفات.
- لا رسائل خاصة بين بالغ وقاصر (تُفرَض على الخادم، لا الواجهة).
- بلاغات عن المستخدمين والغرف والرسائل، حظر متبادل، كتم، إخراج، حظر دائم، سجل إجراءات المشرفين غير قابل للتعديل.
- مراجعة بشرية للبلاغات الحرجة وقناة اعتراض للمستخدم المتضرر.
- Firestore Security Rules + App Check + Play Integrity.
- فلترة نصية أساسية للإساءة بالعربية، مع تسجيل ما يحذف.
- لا بيانات صوتية تُسجَّل افتراضياً. أي تسجيل مستقبلي يحتاج موافقة وسياسة خصوصية.

## 9. الامتثال والبوابات القانونية (قبل تفعيل المال)

قبل فتح أي سحب أو تسوية:
1. موافقة سياسات Google Play على الهدايا الافتراضية والمشتريات داخل التطبيق ونموذج Host/Agency.
2. ترخيص أو متطلبات مزود الدفع/التحويل في بلد العمل.
3. المعالجة الضريبية وVAT وفواتير الوكالات.
4. تحقق KYC من المضيفات والوكالات وعقود موقعة.
5. مراجعة قانونية لمخاطر شبه المقامرة، وللدفع مقابل إرسال الهدايا.

حتى ذلك الحين: النقاط والعمولات تُحسب وتُعرض للمراجعة فقط، **بدون تحويل فعلي**.

## 10. استراتيجية الاختبار

- **وحدة:** حساب العمولة، الشرائح، الصندوق (لا يتجاوز 100%)، التقريب، الانتقال بين الأشهر.
- **تكامل (DB حقيقي):** تزامن الطلبات، Idempotency، الاسترداد/الإلغاء وإعادة الاحتساب، انتقال المضيفة بين الوكالات، منع الاحتساب المزدوج، توازن القيود (مجموع المدين = الدائن).
- **Property-based:** مجموع التوزيعات ≤ الصندوق في آلاف السيناريوهات العشوائية.
- **الصوت:** اختبار فعلي لتأخير الشبكة، فقدان الحزم، الانتقال بين Wi‑Fi وبيانات الجوال.
- **أمان:** محاولات تعديل الدفتر مباشرة، تجاوز الصلاحيات، رموز منتهية.
- **Android:** اختبارات ViewModel وUI (RTL + شاشات متعددة).

## 12. القرارات المعتمدة (21 نوفمبر 2026)

- مزود الصوت: **LiveKit Cloud** (واجهة `VoiceEngine` تُبقي Agora بديلاً).
- التعارض بين المواصفتين: **تُعتمد المواصفة المالية الثانية، والسحب مغلق** خلف Feature Flag.
- الفئة العمرية: **18+ لكل التطبيق**، والمزايا المالية للبالغين الموثَّقين فقط.
- الخادم: **Node.js / TypeScript + PostgreSQL**.
- ما زال مفتوحاً: الدولة/الدول المستهدفة أولاً.

### الأسئلة الأصلية (للتوثيق)

1. مزود الصوت: LiveKit (موصى به) أم Agora؟
2. الدولة/الدول المستهدفة أولاً (تؤثر على الدفع والضرائب)؟
3. هل تعتمد أن المزايا المالية للبالغين فقط، وأن التطبيق نفسه يقبل من 13 أو 16 أو 18+؟
4. اللغة الخلفية: هل تقبل Node.js/TypeScript للخادم؟
5. هل توافق على أن التعارض بين المواصفتين يُحسم لصالح الثانية (مع إبقاء السحب مغلقاً)؟
